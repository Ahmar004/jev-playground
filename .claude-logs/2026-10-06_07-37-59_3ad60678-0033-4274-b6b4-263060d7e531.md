Here's the problem, then what the switch changes.

**How sign-in works today**

When someone presses "Create account" or "Sign in", their browser doesn't talk to Supabase directly. It sends the form to our server on Vercel (`signIn` / `signUp` in `src/server/actions/auth.ts`), and our server calls Supabase. So Supabase sees the request coming from Vercel's server, not from the visitor's laptop.

Our proxy (`src/proxy.ts`) also refreshes each signed-in visitor's session from Vercel's server. That happens about once an hour per visitor, so it's another call Supabase sees coming from Vercel.

**Supabase's limits are per IP address**

From Supabase's rate-limit docs, defaults:
- Sign-ups and sign-ins: 30 per 5 minutes per IP address.
- Token calls (password sign-ins and session refreshes): 150 per 5 minutes per IP address.

These exist to stop one attacker from hammering the login form. They assume each IP is one person. For us, each IP is one of Vercel's servers, shared by everyone.

**What that means on launch day**

Say 500 people click the Discord link in the first 10 minutes and create accounts. Vercel serves them from a handful of servers. After about 30 sign-ups through one server's IP in 5 minutes, Supabase refuses the rest, and visitors see "Too many attempts. Wait a minute and try again." on their very first visit. Everyone shares the same small allowance, so it doesn't matter that each person tried only once.

Session refreshes can hit the same wall: once a few hundred signed-in people pass through one server's IP within 5 minutes, refreshes start failing. Those people then appear signed out and get sent back to the sign-in page.

We haven't seen this locally, because there the browser and server are on the same machine. With 1,000 people, it's likely the first thing to break.

**What IP forwarding does**

Supabase supports this setup directly. Our server adds a header, `Sb-Forwarded-For: <visitor's IP>`, to each call. If the call also carries our secret key, Supabase trusts the header and counts the limit against the visitor's IP instead of Vercel's.

- Each visitor gets their own 30 sign-ins per 5 minutes, which is plenty.
- An attacker hammering the login form is still blocked by IP, and our own Step-19 limits in Postgres stay as a second guard.
- The secret key is already set on Vercel and never reaches the browser.

**Why you need to flip the switch**

Supabase ignores the header unless the project allows it, because otherwise anyone could fake an IP. The switch is in the Supabase dashboard: open the project, then Authentication > Rate Limits > IP Address Forwarding. Turn it on in the production project, and in the dev project so I can prove it works locally before it goes live. I won't change Supabase security settings myself; an earlier step's attempt to do that was blocked.

**The alternative**

You could instead raise the two limits on that same Rate Limits page to large numbers. That needs no code, but Supabase then stops protecting the login form per person, so only our own limits remain. Forwarding keeps both layers, which is why I recommend it.
