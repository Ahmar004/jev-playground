# Tech Stack - Jev's Playground

Status: approved in Step-1 (2026-10-01). Every choice below was weighed against `spec.md`, `ROADMAP.md` and `CLAUDE.md`, not kept because the 8x template ships it.

## Summary

- **App (frontend and backend):** Next.js 16 App Router, React 19, TypeScript, run with `next start` on localhost now and deployable to Vercel unchanged.
- **Data and auth:** Supabase free (Postgres plus Supabase Auth), accessed only through Prisma 7.
- **UI:** Tailwind v4 tokens, Radix primitives, Motion, dnd-kit, hand-built SVG charts, canvas-confetti, next-themes.
- **Model APIs:** plain `fetch` plus Zod, one module per provider (TypeSafe, OpenRouter, Anthropic, OpenAI, Google), shared by the browser and the recording CLI. Content and Recordings are versioned JSON in the repo.
- **Quality and observability:** Vitest, Playwright, k6, Sentry, PostHog, Pino.

## Constraints that shape it

- **Localhost now, Vercel later (Rule-9).** Code must run unchanged on serverless functions. So the database is hosted (Vercel can't reach a laptop), nothing writes files at runtime, and no state lives in one process's memory: rate limits, sessions and share counts live in Postgres.
- **1,000+ users and a 2-second phone load (R75, R79).** Whatever is the same for every user is prerendered and served from the CDN. Functions only handle per-user data and the TypeSafe pass-through.
- **Keys (Rule-8, spec 4).** Keys live in React memory. Four providers are called straight from the browser. Only TypeSafe-key calls touch our server, and the pass-through never logs or stores the key or the body.
- **$50 and a 2026-10-03 deadline (Rule-0.1, Rule-1).** Every service is on a free tier. Libraries are picked for low wiring time.

## Architecture

```
Browser (React client, keys in tab memory only)
 |- Prerendered pages + Recordings  <- CDN (built from JSON in the repo)
 |- OpenRouter / Anthropic / OpenAI / Google  <- direct fetch with the user's key (R17)
 '- Next.js server (`next start` now, Vercel functions later)
      |- proxy.ts          session gate; redirects to Sign-in (shared results exempt)
      |- Server Actions    progress, checks, quizzes, XP, badges, leaderboard, shares
      |- /api/jev (Node)   TypeSafe pass-through; never logs key or body (R18)
      '- Prisma 7 -> Supabase Postgres (pooled connection)
Recording CLI (`pnpm record`, owner's machine) -> same runner -> content/recordings/*.json -> git
```

## Rendering strategy

Next.js 16 Cache Components (`cacheComponents: true`) let each page mix a prerendered shell with per-request parts, so each kind of page gets the strategy that fits it.

| Pages                                                                                                 | Strategy                                                                                                            | Reason                                                                                                              |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Sign-in, Glossary, Methodology; the content of Level, Game, Arena presets, Sandbox templates, Quizzes | SSG: prerendered at build from `content/`                                                                           | Identical for every user. Served from the CDN worldwide, fast on phones (R79), no server cost at 1,000 users (R75). |
| Home, Path, Profile, Leaderboard, header progress bar                                                 | PPR: static shell plus per-user parts rendered on the server per request, streamed inside `<Suspense>`              | The shell paints at once. Only the user's own numbers wait on the database.                                         |
| Game runtime, Arena runs, Sandbox builder, Keys panel, mode switch, replays                           | CSR: client components                                                                                              | They depend on in-memory keys, timers and animation. Replays run in the browser at recorded latency (R7).           |
| Shared result                                                                                         | On-demand cached SSR (ISR-like): `'use cache'` + `cacheTag(shareId)`, expired with `updateTag` on delete, `noindex` | A snapshot never changes, so the first render is cached. Deleting it takes effect at once (R87).                    |

A single strategy loses: full SSR re-renders unchanging content on every request and is slower for distant users, and a full SPA shows a blank screen on phones until the bundle loads. `proxy.ts` gates every page except shared results with an optimistic session check. Every read or write of user data re-checks the session and ownership on the server (`docs/rules/auth.md`).

## Recording cost estimate (spec 17)

Prices on 2026-09-25, per million tokens (input/output): Haiku 4.5 $1/$5, Sonnet 5.5 $2/$10, Opus 5.5 $4/$20, Jev $0.042/free. About 250 items x 3 Claude models at roughly 800 input and 300 output tokens comes to **about $5-10 per full run**. Opus 5.5 can't turn thinking off, so it records at low effort. Step-3 fixes the item counts, and the CLI's dry run confirms the cost before any spend.

## Vercel readiness (Rule-9)

- No runtime file writes. Recordings are build-time files, and only the local CLI writes them.
- No cross-request memory. Rate limits (for example, shares per user) are counted in Postgres.
- Pooled database connections. Functions stay short: the pass-through only forwards.
- Launch steps: push to a personal repo, import it into Vercel, set env vars, set the function region next to the database, then add Resend SMTP for password reset.
