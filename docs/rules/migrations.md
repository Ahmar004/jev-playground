# Migrations

**The generator writes the migration. You write the schema.**

On this project migrations are generated and applied locally, against our
own database (8x confirmed this; GitHub CI is disabled).

Prisma 7 takes the database from `prisma.config.ts`, which loads `.env.local`
and uses `DIRECT_URL` (the session pooler, port 5432), so `migrate deploy`
needs no URL argument. The scripts below pass their `--db-url` to the CLI as
`DIRECT_URL`.

- Never create or edit files under `prisma/schema/migrations/` by hand —
  every file there is generated by `scripts/generate-migration.mjs`.
- The flow, after changing `prisma/schema/*.prisma` and running
  `pnpm prisma:generate`:
  1. `pnpm exec prisma migrate deploy` replays the committed migrations onto
     the local database.
  2. `node scripts/generate-migration.mjs --name <name> --db-url <url>`
     diffs that database against the schema and writes the missing
     migration. `--check` previews it without writing.
  3. `pnpm exec prisma migrate deploy` again applies the new migration.
  4. `pnpm db:run-once`, then `pnpm check:rls`.
  5. Commit the generated migration with the schema change that caused it.
- **A refusal from the generator is real.** Exit 2 means `prisma migrate
diff` emitted a destructive pattern like `DROP COLUMN`/`SET NOT NULL`,
  which needs hand-written data-preserving SQL via
  `prisma migrate dev --create-only` instead — the one sanctioned exception
  to "never hand-write a migration".
- The other sanctioned hand-written migration is
  `ALTER TABLE "<table>" ENABLE ROW LEVEL SECURITY;` for each new table —
  the Prisma schema can't express it (`docs/rules/auth.md`), and
  `pnpm check:rls` stays red until it exists. Nothing else in the file: no
  policies, never `FORCE`.
- No SQL-editor writes against the database, ever, for schema or data.
  One-off data fixes go in `prisma/run-once.sql` (next section).

## Run-once SQL — `prisma/run-once.sql`

The one SQL file outside `migrations/` that you hand-write. Whatever it
holds runs **once per database**, when `pnpm db:run-once` runs right after
`prisma migrate deploy`. It is for one-off changes that aren't a schema change — fix a value,
insert reference rows, backfill a column, replace a view, add an extension
or a grant.

**Using it.** Replace the file's content with the new one-off (don't append
to the last one — it already ran), then run `pnpm db:run-once` against the
local database.

**How "once" works.** `scripts/run-once-sql.mjs` hashes the file's
executable content — comments and whitespace don't count, so a doc tweak
never re-runs anything — and skips any version already recorded in the
`_run_once_sql` ledger (`prisma/schema/run-once-sql.prisma`). The ledger row
and the SQL go to Postgres as one command, in one implicit transaction: both
land or neither does, so a failed run is retried on the next run and a
successful one cannot repeat. Query the ledger to see what has run where and
when. To run the same SQL again on purpose, a statement has to change; a
comment won't do it.

- **Not a schema side-channel.** Tables, columns, indexes, and enums belong
  in `prisma/schema/*.prisma`; `prisma migrate diff --exit-code` fails if
  this file created anything Prisma tracks.
- **It may run on an empty database.** Write it so that matching nothing is
  fine (an `UPDATE ... WHERE` that finds no rows), and guard an `INSERT`
  that needs existing rows (`INSERT ... SELECT ... WHERE EXISTS`).
- **One transaction.** Nothing that refuses to run inside a transaction
  block (`CREATE INDEX CONCURRENTLY`, `VACUUM`).
- **Merge conflict in this file? Keep only your SQL.** The other side's
  version was applied under its own hash; keeping both makes a new version
  that runs the old one-off again.
- The order is migrations → this file, so the file may use a table the same
  change's migration creates.

Note: this repo's Prisma-schema-only workflow is a deliberate, different
choice from the Supabase-CLI workflow used elsewhere in the org
(`supabase migration new`, `NOTIFY pgrst`) — those conventions do not
apply here. See the design guide's "central decision" section for why
Prisma's generated-migration model was chosen over the Supabase-CLI
alternative.
